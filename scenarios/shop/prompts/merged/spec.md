# Maker shops — backend

We run a platform that hosts online shops for small independent makers: a pottery studio, a
clothing label, a store for phone and laptop accessories. Each shop manages its products and stock,
and customers order from them. The shops are small, but they sell every day, and some run limited
drops where many customers order at the same moment.

Build the backend API (no UI). This is the complete specification.

## Database
{database}

## Deployment
Our platform deploys the app by running `./start.sh` from the repository root, with `PORT`
and the database environment variables set. The app must serve the API on `PORT`.

## Shops
Every record belongs to a shop, identified by a `shopId` string that we assign (e.g.
`clay-and-kiln`). There is no endpoint for shops. A record may only reference records of the same
shop, and lists only ever return records of the requested shop.

## Money
Prices and amounts are numbers in the shop's currency with at most 2 decimals. Amounts the app
computes are rounded to the cent (half up).

# 1. Products

## 1.1 Products, options and variants
Northloom sells the same shirt in five sizes and three colours. A product has `options`, the names
of the ways it varies, and `variants`, each with its own sku, price and stock:
```json
{ "id": "…", "shopId": "northloom", "name": "Linen tee", "category": "tops",
  "options": ["size", "colour"],
  "variants": [
    { "id": "…", "sku": "TEE-S-BLACK", "options": { "size": "S", "colour": "black" }, "price": 25, "stock": 10 },
    { "id": "…", "sku": "TEE-M-BLACK", "options": { "size": "M", "colour": "black" }, "price": 25, "stock": 0 }
  ] }
```
`POST /products`
```json
{ "shopId": "northloom", "name": "Linen tee", "category": "tops", "options": ["size", "colour"],
  "variants": [ { "sku": "TEE-S-BLACK", "options": { "size": "S", "colour": "black" }, "price": 25, "stock": 10 } ] }
```
- `name` and `category` are required, non-empty strings.
- A product has at least one variant. Every variant has a `sku`, a non-empty string, unique within
  the shop across all products and variants → `409` if the shop already has it; `options` with
  exactly the product's option names, each a non-empty string; `price`, a number ≥ 0 with at most
  2 decimals; and `stock`, an integer ≥ 0. No two variants of a product may have the same option
  values → `400`. Variant ids are generated by the server.
- A request with `variants` must not also have the product-level `sku`, `price` or `stock` → `400`.
- Invalid requests → `400` with an error message, and nothing is stored.

→ `201` with the product, including a server-generated `id`. Responses always include `options` and
`variants`.

`GET /products/:id` → the product.

### Simple products
Most products don't vary, and our shop admin and several shops' own integrations use a simpler
shape for them:
```json
{ "shopId": "clay-and-kiln", "sku": "MUG-SPECKLED", "name": "Speckled mug", "category": "mugs",
  "price": 24.5, "stock": 40 }
```
- `POST /products` with `sku`, `price` and `stock` (no `variants`) creates a product with
  `"options": []` and one variant with those values and `"options": {}`. They are validated like a
  variant's (`409` for a taken sku).
- Product responses always include `sku` and `price`, set to those of the first variant, and
  `stock`, the total stock of all variants.

### Changing products
- `PATCH /products/:id` with any of `name`, `category`, `price`, `stock` (and the other product
  fields below) changes only those fields (same validation) → `200` with the product. `price` and
  `stock` change the product's only variant; `400` if the product has several variants.
- The `sku` can't be changed with `PATCH /products/:id` → `400`. `PATCH /products/:id` with
  `options` or `variants` → `400`.
- `POST /products/:id/variants` with a variant (`sku`, `options`, `price`, `stock`) adds it → `201`
  with the product.
- `PATCH /products/:id/variants/:variantId` with any of `price`, `stock` → `200` with the product.

## 1.2 Listing products
`GET /products?shopId=clay-and-kiln` → that shop's products.
- Filters: `category`; `sku` (matches any variant's sku); `inStock=true` (products with any variant
  that has units available, see Carts); `option.<name>=<value>`, e.g. `?option.size=M` (products with
  a variant that has that option value). More filters are described with the features below.
  Multiple filters are ANDed.
- `?limit=` (default 50, max 500).

## 1.3 Category attributes
Every category has its own product details: a mug has a capacity and is dishwasher safe or not, a
shirt has a material, a cable a length and a connector. Shops want to record them, and customers
want to filter by them.

### Definitions
`POST /shops/:shopId/categories/:category/attributes`
```json
{ "key": "capacity_ml", "label": "Capacity (ml)", "type": "number" }
```
- `key`: letters, digits and underscores; unique within the shop and category → `409` otherwise.
- `label`: a non-empty string.
- `type`: `text`, `number`, `boolean` or `select`. A `select` needs `options`, a non-empty list of
  distinct strings.
- Invalid definitions → `400`.

→ `201` with the definition.

`GET /shops/:shopId/categories/:category/attributes` → the category's definitions, in the order
they were created.

### Values
- Products have `attributes`, values for the attributes of their category:
  `"attributes": { "capacity_ml": 350, "dishwasher_safe": true }`. Responses always include it
  (`{}` if there are none).
- `POST /products` and `PATCH /products/:id` accept `attributes`. A key the product's category
  doesn't define, or a value of the wrong type (for a `select`, a value not among its options) →
  `400`, and nothing changes.
- `PATCH` merges into the existing attributes; `null` removes an attribute.
- When a product moves to another category, it keeps the attributes that the new category also
  defines with the same type; the others are removed. Attributes in the same request are
  validated against the new category.

### Filters
`GET /products?shopId=clay-and-kiln&category=mugs&attr.dishwasher_safe=true&attr.capacity_ml.min=300`
- `attr.<key>=<value>`: products with exactly that value (numbers compared as numbers, booleans
  written `true`/`false`).
- `attr.<key>.min` and `attr.<key>.max`: inclusive bounds for `number` attributes.
- Attribute filters need a `category` filter, and the attribute must be defined for that category →
  `400` otherwise.

### Facets
`GET /products/facets?shopId=clay-and-kiln&category=mugs`, plus any of the product filters →
```json
{ "total": 12,
  "attributes": { "dishwasher_safe": { "true": 8, "false": 3 }, "glaze": { "matte": 5, "gloss": 7 } } }
```
- `total`: the number of products matching the filters.
- For every `select` and `boolean` attribute of the category: how many of the matching products have
  each value, listing only values that at least one product has.
- `category` is required → `400` without it.

## 1.4 Personalisation fields
Clay & Kiln engraves names on mugs, Northloom embroiders initials, and some items can be gift
wrapped. What can be personalised differs from product to product.

Products have `personalization`, the fields a customer fills in when ordering:
```json
"personalization": [
  { "key": "engraving", "label": "Name to engrave", "type": "text", "required": true, "maxLength": 20 },
  { "key": "font", "label": "Font", "type": "select", "options": ["serif", "script"] },
  { "key": "gift_wrap", "label": "Gift wrap", "type": "boolean" }
]
```
- `key`: letters, digits and underscores, unique within the list. `label`: a non-empty string.
- `type`: `text`, `select` or `boolean`. A `select` needs `options`, a non-empty list of distinct
  strings. A `text` field may have a `maxLength` (an integer ≥ 1).
- `required`: `true` or `false` (default `false`).
- `POST /products` and `PATCH /products/:id` accept `personalization`; a `PATCH` replaces the whole
  list. Invalid fields → `400`. Responses always include it (`[]` if there are none).

How customers fill them in is described under Orders.

## 1.5 Descriptions
Products have `description`: optional text of at most 5000 characters. `POST /products` and
`PATCH /products/:id` accept it (`null` clears it).

## 1.6 Active products
Products have `active` (default `true`; `PATCH /products/:id` accepts it). Inactive products can't be
ordered or put in carts (`400`) and don't appear in search; `GET /products` still lists them, and
accepts the filter `active=true|false`.

## 1.7 Best sellers
Shops want to show their best sellers first.

- Products show `unitsSold`: the units of the product (all its variants) in orders that aren't
  cancelled, minus the units returned. It is always current.
- `GET /products?shopId=clay-and-kiln&sort=bestselling` lists the most units sold first; products
  with the same number by `name` (A to Z). It works with the product filters and `limit`.

## 1.8 Reviews and ratings
Shoppers trust products that other customers liked, and shops want to hear what buyers think.

`POST /products/:id/reviews`
```json
{ "customerEmail": "ines@example.com", "rating": 5, "title": "Lovely glaze", "text": "Holds a big coffee." }
```
- `rating`: an integer from 1 to 5. `text`: a non-empty string of at most 2000 characters. `title`:
  optional, at most 100 characters. Invalid requests → `400`.
- Only customers who ordered the product (any of its variants), in an order that isn't cancelled, may
  review it (`customerEmail` ignoring case) → `403` otherwise.
- One review per customer and product → `409` for a second one.

→ `201` with the review: `id`, `productId`, `customerEmail`, `rating`, `title`, `text`, `createdAt`,
`status` (`published`) and `helpful` (0).

- `PATCH /reviews/:id` with any of `rating`, `title`, `text` (same validation), or `status`
  (`published` or `hidden`, for moderation) → `200` with the review.
- `POST /reviews/:id/helpful` with `{ "customerEmail": "…" }` → `200` with the review. Each email
  counts once (ignoring case); voting again changes nothing.
- `GET /products/:id/reviews` → the product's published reviews, newest first; `?sort=helpful` puts
  the most helpful first (ties newest first); `?rating=5` only those with that rating; `?limit=`
  (default 20, max 100).

Ratings on products:
- Products have `rating`: `{ "average": 4.3, "count": 12 }` over their published reviews, the average
  rounded to 1 decimal; `{ "average": null, "count": 0 }` without any. Always current.
- Product filter `minRating=4` (average at least that).
- `GET /products?sort=rating`: highest average first, then most reviews, then `name`; products without
  reviews last.

## 1.9 Search
Customers want a search box that finds products while they type.

- `GET /products/search?shopId=clay-and-kiln&q=speck mug` → `{ "results": [ …products as GET returns
  them… ] }`, at most `limit` (default 20, max 100). `q` is required (`400`).
- What is searched: the name, description and category, the skus of the variants, and the text and
  `select` attribute values.
- Matching works by word, ignoring case and accents. Every word of `q` must match. A word also matches
  other grammatical forms of the same English word (`mug` and `mugs`). The last word of `q` also
  matches words that start with it, as the customer may still be typing (`speck` finds "Speckled").
  A `q` that is a whole sku finds that product (ignoring case).
- Order: products whose name contains all the words first; within each group, most `unitsSold`
  first, then by `name`.
- It combines with the product filters `category`, `inStock` and `minRating`.
- Search always reflects the current data.

## 1.10 Languages and translations
Clay & Kiln sells to Portugal and Germany, and customers there want product pages in their language.

### Languages
`PUT /shops/:shopId/languages` with `{ "default": "en", "others": ["pt", "de"] }` → `200`. Codes are
two lower-case letters; the default isn't among the others (`400` otherwise). `GET` returns them;
shops that never set any have `{ "default": "en", "others": [] }`.

### Translations
Products have `translations`, per language of `others`:
```json
"translations": {
  "pt": { "name": "Caneca salpicada", "description": "…", "options": { "black": "preto", "M": "Médio" } }
}
```
- `name` (non-empty) and `description` translate the product's; `options` translates variant option
  values (keyed by the value in the default language). Every part is optional.
- `POST /products` and `PATCH /products/:id` accept `translations`. A `PATCH` merges per language:
  the fields it sends replace those fields (`options` as a whole), `null` removes a field, and a
  language set to `null` is removed. A language the shop doesn't have → `400`.
- Responses always include `translations` (`{}` if there are none).

### Reading in a language
- `GET /products/:id`, `GET /products` and `/products/search` accept `?lang=pt`: `name`,
  `description` and the variants' option values come in that language where translated, otherwise in
  the default language. A language the shop doesn't have → `400`.
- Search with `lang` searches the texts in that language (falling back the same way). Word forms only
  need to work for English.
- Product filter `missingTranslation=pt`: products without a `name` in that language.

## 1.11 Importing listings from Craftly
Many of our makers also sell on the Craftly marketplace and want to bring their listings over, and
keep names, descriptions and prices in sync by importing again from time to time.

`POST /shops/:shopId/imports/craftly` with Craftly's export, as is:
```json
{ "listings": [
  { "listing_id": 9001, "title": "Speckled mug", "description": "…", "state": "active",
    "taxonomy_path": ["Home & Living", "Kitchen", "Mugs"], "tags": ["stoneware"],
    "price": { "amount": 2450, "divisor": 100, "currency_code": "EUR" }, "quantity": 12, "sku": ["MUG-SPECKLED"] },
  { "listing_id": 9002, "title": "Linen tee", "state": "inactive", "taxonomy_path": ["Clothing", "Tops"],
    "variations": {
      "properties": [ { "property_id": 1, "name": "Size" }, { "property_id": 2, "name": "Colour" } ],
      "offerings": [ { "sku": "TEE-S-RED", "values": { "1": "S", "2": "Red" },
                       "price": { "amount": 3000, "divisor": 100, "currency_code": "EUR" }, "quantity": 4 } ] } }
] }
```
- A listing becomes a product: `name` from `title`, `description`, `category` from the last entry of
  `taxonomy_path` in lower case. Without `variations` it has one variant (the first `sku`, `price`,
  `quantity` as stock); with them, the option names are the property names in lower case, and every
  offering is a variant (its values by `property_id`). Prices are `amount / divisor`.
- A listing in state `inactive` makes the product inactive (`"active": false`), `active` makes it
  `true`.
- Imported products remember where they came from: `source: { "marketplace": "craftly", "listingId":
  "9001" }`, included wherever a product is returned (`null` for other products); `GET
  /products/:id/source` → the listing exactly as last imported.
- Importing again updates the product with the same `listingId`: name, description, category, active,
  prices; variants are matched by sku, new offerings are added. Stock is only taken from Craftly when a
  product or variant is created: after that the shop's own stock counts.
- A listing that can't be imported (missing title or price, a sku another product of the shop has) is
  skipped and reported; the others are imported.
- → `200` with `{ "created": 3, "updated": 1, "unchanged": 40, "rejected": [ { "listingId": "9003",
  "error": "…" } ] }`. Importing the same export again changes nothing.
- Exports have up to 2,000 listings; the response must come within 60 seconds.

# 2. Orders

## 2.1 Placing orders
`POST /orders`
```json
{ "shopId": "clay-and-kiln", "customerEmail": "ines@example.com",
  "items": [ { "variantId": "…", "quantity": 2 } ] }
```
- `customerEmail` is required and must contain exactly one `@`, with text on both sides.
- `items`: at least one; `quantity` an integer ≥ 1. An item names a `variantId`, a variant of a
  product of the same shop. An item with only a `productId` (as the simple-product integrations send
  it: `{ "productId": "…", "quantity": 2 }`) works for products with exactly one variant; `400` for
  products with several. An item with both must have a variant of that product (`400` otherwise).
- Items of inactive products → `400`.
- An item may have `personalization`, see 2.2. The same variant may appear more than once only if
  the items' personalisation differs (two mugs with different names); the same variant twice with
  the same personalisation → `400`.
- Optional: `discountCode` (see 2.4), `lang` (see 2.3), `delivery` (see 2.5).
- Invalid requests → `400`, and nothing is stored.
- If there isn't enough stock available for any of the variants (for the variant's total quantity
  in the order) → `409`, and nothing changes: no stock is taken and no order is created.
- Otherwise the stock of every variant is reduced by the quantity ordered.
- Many customers order at the same time, especially during limited drops. Stock must never go below
  0, and we must never sell more than we have.

→ `201` with the order:
```json
{
  "id": "…", "number": 1042, "shopId": "clay-and-kiln", "customerEmail": "ines@example.com",
  "status": "placed", "createdAt": "2026-10-02T09:15:00Z", "version": 1,
  "items": [
    { "id": "…", "productId": "…", "variantId": "…", "sku": "MUG-SPECKLED", "name": "Speckled mug",
      "options": {}, "unitPrice": 24.5, "quantity": 2, "lineTotal": 49, "discount": 0,
      "personalization": {}, "returnedQuantity": 0 }
  ],
  "subtotal": 49, "discount": null, "delivery": null, "shippingFee": 0, "total": 49, "refunded": 0
}
```
- Every order line has an `id`, which never changes.
- `productId`, `variantId`, `sku` (the variant's), `name` (the product's), `options` (the variant's)
  and `unitPrice` (the variant's price) are as at the time of the order: later changes to the
  product don't change existing orders.
- `lineTotal` is `unitPrice` × `quantity`; `subtotal` is the sum of the line totals; `total` is
  `subtotal` − the discount amount + `shippingFee`.
- `returnedQuantity` is 0 until something is returned; `refunded` is the total refunded so far (see
  2.6).

### Order numbers
Customers call about "my order", and nobody can read our order ids out over the phone.
- Every order gets a `number`: per shop, 1001 for the shop's first order, then 1002, and so on, in
  the order the orders were placed.
- Numbers are never reused or skipped: a rejected order doesn't take a number, and a cancelled order
  keeps its number. Orders placed at the same moment still get distinct numbers, without gaps.
- `number` appears wherever orders appear.

### Reading and listing orders
`GET /orders/:id` → the order.

`GET /orders?shopId=clay-and-kiln` → that shop's orders.
- Filters: `customerEmail` (case-insensitive); `status`; `productId` (orders with any variant of that
  product); `variantId`; `number`, e.g. `&number=1042`; `personalization.<key>=<value>` (orders with a
  line that has that value, booleans written `true`/`false`, e.g. all orders with gift wrapping);
  `discountCode` (ignoring case); `pickupPointId`; `subscriptionId`. Multiple filters are ANDed.
- `?limit=` (default 50, max 500).

### Cancelling
`POST /orders/:id/cancel` → `200` with the order, now `"status": "cancelled"`; the ordered
quantities go back into stock. Only orders with status `placed` can be cancelled → `409` otherwise.
Cancelling an order frees its use of a discount code.

## 2.2 Personalised items
- Order items take `personalization`, the customer's values:
  `{ "variantId": "…", "quantity": 1, "personalization": { "engraving": "Ana", "gift_wrap": true } }`.
- The values are checked against the product's fields at the time of the order: every required field
  is present (a required text is not empty), there are no other keys, and every value has the
  field's type, fits its `maxLength` and is one of its `options` → `400` otherwise. Items of a
  product without fields can't have personalisation → `400`.
- Order lines show `personalization` exactly as sent (`{}` if there is none).
- Changing a product's fields later doesn't change existing orders.

## 2.3 Orders in a language
`POST /orders` accepts `lang`; the lines' `name` and `options` are then in that language (with the
same fallback as for reading products), as at the time of the order.

## 2.4 Discount codes
Shops want to hand out discount codes: to newsletter subscribers, for a weekend sale, or a few codes
that only the first customers of a drop can use.

### Codes
`POST /shops/:shopId/discounts`
```json
{ "code": "WINTER10", "type": "percent", "value": 10, "minSubtotal": 50, "maxUses": 100,
  "oncePerCustomer": true, "startsAt": "2026-12-01T00:00:00Z", "endsAt": "2027-01-01T00:00:00Z" }
```
- `code`: letters, digits, `-` and `_`; unique within the shop, ignoring case → `409` otherwise.
- `type`: `percent` (a `value` above 0 and at most 100) or `fixed` (an amount above 0).
- Optional: `minSubtotal` (an amount ≥ 0), `maxUses` (an integer ≥ 1), `oncePerCustomer` (a boolean,
  default `false`), `startsAt` and `endsAt` (ISO 8601 timestamps).
- Invalid codes → `400`.

→ `201` with the code, including `"active": true` and `"uses": 0`.

`GET /shops/:shopId/discounts` → the shop's codes. `GET /shops/:shopId/discounts/:code` (the code
ignoring case) → the code. `uses` is the number of orders that used the code and aren't cancelled.

`PATCH /shops/:shopId/discounts/:code` with `active` (`true` or `false`) → `200` with the code.

### Orders with a code
- `POST /orders` accepts `discountCode` (ignoring case).
- The code must exist in the shop and be active; the time of the order must be at or after
  `startsAt` and before `endsAt`; the order's subtotal must be at least `minSubtotal`; `uses` must be
  below `maxUses`; and with `oncePerCustomer`, the customer (`customerEmail`, ignoring case) must not
  have another order with this code that isn't cancelled. Otherwise → `400` with a message saying
  why, and nothing is stored.
- Orders with a code have `discount`:
  ```json
  "subtotal": 100, "discount": { "code": "WINTER10", "amount": 10 }, "total": 90
  ```
  - `code` is written as the shop defined it.
  - `percent`: `amount` is the subtotal × `value` / 100, rounded. `fixed`: the `value`, but at most
    the subtotal.
- Every order line has `discount`, its share of the amount: proportional to its line total and
  rounded, except that the last line gets whatever makes the shares add up exactly to the amount.
- Orders without a code: `discount` `null` or omitted, and every line's `discount` 0.
- Codes are used in drops, where many customers order at the same moment: `maxUses` and
  `oncePerCustomer` must hold even then.

## 2.5 Local delivery and pickup points
Shops deliver locally with their own couriers, and customers can pick orders up at partner shops.

### Delivery zones
`POST /shops/:shopId/delivery-zones`
```json
{ "name": "Lisbon centre", "area": [[-9.20, 38.69], [-9.10, 38.69], [-9.10, 38.75], [-9.20, 38.75]],
  "fee": 4.5, "freeFrom": 60 }
```
- `area`: a polygon, at least 3 corners as `[lng, lat]`, in order (it may repeat the first corner at the
  end). `fee`: an amount. `freeFrom`: optional amount. Invalid → `400`.
- → `201` with the zone, including `id`. `GET /shops/:shopId/delivery-zones`; `DELETE
  /delivery-zones/:id` (`204`).

### Pickup points
- `POST /shops/:shopId/pickup-points` with `{ "name", "location": { "lat", "lng" } }` → `201`.
- `GET /shops/:shopId/pickup-points?near=38.72,-9.14` → nearest first, each with `distanceKm`
  (great-circle distance, 1 decimal); `?limit=`. Without `near`, all of them.

### Orders
Orders (and cart checkouts) accept `delivery`:
- `{ "type": "shipping", "location": { "lat", "lng" } }`: the location must be inside a zone of the
  shop (`400` otherwise). If several zones contain it, the cheapest applies. `shippingFee` is the
  zone's `fee`, or 0 if the order's subtotal minus its discount is at least `freeFrom`.
- `{ "type": "pickup", "pickupPointId": "…" }` (a pickup point of the shop): `shippingFee` 0.
- Without `delivery`: `shippingFee` 0.

Orders show `delivery` (with the `zoneId` that applied for shipping) and `shippingFee`. Returns never
refund the shipping fee; sales reports are based on the lines.

## 2.6 Returns
Customers send items back: a mug arrived chipped, a shirt doesn't fit. Shops need to record returns
and refund the right amount.

`POST /orders/:id/returns`
```json
{ "items": [ { "lineId": "…", "quantity": 1 } ], "reason": "arrived chipped" }
```
- `items`: at least one; `lineId` a line of this order; `quantity` an integer ≥ 1; a line at most
  once. `reason` is an optional string. Invalid requests → `400`.
- Lines with personalisation can't be returned → `400`.
- Cancelled orders → `409`.
- An item returning more units than the line has left (its quantity minus the units already
  returned) → `409`.
- Nothing changes when a return is rejected.

→ `201` with the return:
```json
{ "id": "…", "orderId": "…", "createdAt": "2026-12-28T10:02:00Z", "reason": "arrived chipped",
  "items": [ { "lineId": "…", "quantity": 1, "refund": 22.05 } ], "refund": 22.05 }
```
- What a line was paid is its line total minus its discount. An item refunds the returned share of
  that: paid × returned quantity / line quantity, rounded. When a return brings a line's
  `returnedQuantity` up to its quantity, it refunds whatever of the line's paid amount hasn't been
  refunded yet, so the refunds of a line always add up exactly to what was paid for it.
- `refund` is the sum of the items' refunds.
- Returned units go back into the variant's stock.
- The order: `returnedQuantity` per line, `refunded` (the total refunded so far, 0 if nothing), and
  status `partially_returned` after the first return, `returned` once every unit of every line has
  been returned. Returned and partially returned orders can't be cancelled → `409`.
- A return doesn't free the use of a discount code.
- `GET /orders/:id/returns` → the order's returns, oldest first.
- Customers and support staff sometimes submit the same return at the same moment: an order must
  never have more units returned than ordered, or more refunded than paid.

## 2.7 Changing orders
Customers write in before their order ships: another size, one more mug, drop the scarf.

- Orders have `version`: 1 when placed, increased by every change to the order (edits, cancelling,
  returns).
- `PATCH /orders/:id` with `{ "version": 2, "items": [ … ] }`, the complete new list of items as in
  `POST /orders`, → `200` with the order:
  - Only `placed` orders can be changed (`409` otherwise), and `version` must be the order's current
    one (`409` if it changed in the meantime, e.g. two support staff editing at once).
  - Items are validated as for a new order (`400`).
  - A line that stays (same variant and personalisation) keeps its `id` and `unitPrice`, with the new
    quantity; new lines get the current price.
  - Stock: what the new list needs more is taken, what it needs less is returned, all or nothing (not
    enough stock → `409`, nothing changes).
  - The discount is recomputed for the new subtotal with the order's code (its `minSubtotal` must
    still be met → `400`; limits on uses aren't checked again), with new line shares. The shipping
    fee is recomputed too.
  - `number`, `createdAt`, `customerEmail` and `delivery` don't change.
- `GET /orders/:id/revisions` → every earlier version of the order, complete as it was, oldest first.

# 3. Carts that hold stock
During drops, customers lose items between choosing them and paying. Carts hold the stock for
a while.

## 3.1 Settings
`PUT /shops/:shopId/settings` with `{ "cartHoldSeconds": 900 }` (an integer from 5 to 86400) → `200`.
`GET` returns it; the default is 900.

## 3.2 Carts
- `POST /carts` with `{ "shopId", "customerEmail" }` (validated like orders) → `201`:
  `{ "id", "shopId", "customerEmail", "status": "active", "items": [], "expiresAt": "…" }`.
- `PUT /carts/:id/items/:variantId` with `{ "quantity": 2 }` sets the cart's quantity of that variant
  (`0` removes it) → `200` with the cart. Products with personalisation fields can't go into carts
  (`400`). Each change renews the hold: `expiresAt` becomes now + `cartHoldSeconds`.
- Items show `variantId`, `productId`, `sku`, `quantity`, the current `unitPrice` and `lineTotal`;
  the cart shows `total`.
- `GET /carts/:id`; `DELETE /carts/:id` → `204`, releasing what it held.

## 3.3 Holding stock
- Units in active carts are held: variants and products have `available`, the stock minus the units
  held. `stock` stays the units the shop has.
- Orders (without a cart), cart changes and the `inStock` filter use `available`. Not enough → `409`,
  and nothing changes.
- A cart whose `expiresAt` has passed is `expired`: its units are available again at once, without
  waiting for any cleanup to run.
- Many customers fill carts at the same moment in a drop: never hold or sell more than the stock.

## 3.4 Checkout
`POST /carts/:id/checkout` with optional `discountCode` (and the other order fields that aren't items)
→ `201` with the order, placed like `POST /orders` with the cart's items, which may use the units the
cart holds. The cart becomes `checked_out`. An expired or checked-out cart → `409`; an empty cart →
`400`.

# 4. Subscriptions
Some products are bought again and again: Northloom's sock club, refills of screen protectors. Customers
want to subscribe and get them on a schedule.

## 4.1 Subscriptions
`POST /subscriptions`
```json
{ "shopId": "northloom", "customerEmail": "ines@example.com", "items": [ { "variantId": "…", "quantity": 2 } ],
  "everyWeeks": 4, "startsOn": "2027-05-01" }
```
- `items` like an order's, but without personalisation (an item with `personalization` → `400`);
  `everyWeeks` an integer from 1 to 52; `startsOn` a
  date. Also optional `delivery`, as for orders. Invalid → `400`.
- → `201` with the subscription: also `id`, `status` (`active`), `nextOn` (the next scheduled date,
  first `startsOn`) and `history` (`[]`).
- The schedule is `startsOn`, then every `everyWeeks` weeks after it.
- `GET /subscriptions/:id`; `GET /subscriptions?shopId=…` with filters `customerEmail` (ignoring case)
  and `status`.
- `PATCH /subscriptions/:id` with any of `status` (`active`, `paused`, `cancelled`), `items`,
  `everyWeeks` → `200`. Cancelled subscriptions can't change (`409`). When a paused subscription is
  resumed, `nextOn` becomes the first date of its schedule on or after today (UTC); missed dates are
  skipped.

## 4.2 Placing the orders
Our scheduler calls `POST /shops/:shopId/subscriptions/run` with `{ "date": "2027-05-01" }` every day.
Sometimes it calls twice for the same day, and two instances may call at the same moment.
- Every active subscription of the shop with `nextOn` on or before `date` gets one order, placed like
  `POST /orders` (current prices, stock, delivery), with `subscriptionId` on the order. `nextOn` then
  moves to the first date of the schedule after `date`.
- If an order can't be placed (not enough stock, a delivery location no longer in a zone), it is
  skipped, and `nextOn` moves on just the same.
- `history` gets an entry per scheduled date handled: `{ "date", "orderId" }`, or `{ "date",
  "skipped": "<reason>" }`.
- → `200` with `{ "placed": [orderIds], "skipped": [subscriptionIds] }`. However often and
  concurrently it is called, a subscription never gets two orders for the same scheduled date.

# 5. Stock history
Shops need to know why stock changed: for audits, to find shrinkage, and to settle disputes with
customers.

- Every change to a variant's stock is recorded as a movement:
  ```json
  { "id": "…", "variantId": "…", "productId": "…", "change": -2, "stockAfter": 8, "reason": "order",
    "orderId": "…", "at": "2027-05-26T09:00:00Z" }
  ```
  `reason` is one of `initial` (a new product or variant, or one created by an import), `order`
  (also subscriptions and checkouts), `cancel`, `return`, `edit` and `adjustment` (stock set with
  `PATCH`, or below). `orderId` is set for order, cancel, return and edit. Cart holds don't change
  the stock and have no movements.
- `POST /variants/:id/adjustments` with `{ "change": -3, "note": "broken in storage" }` (a non-zero
  integer; stock can't go below 0 → `409`) → `201` with the movement, which also has the `note`.
- `GET /variants/:id/movements` → oldest first, with `from` and `to` (timestamps, inclusive) and
  `?limit=` (default 100, max 1000).
- `GET /reports/stock?shopId=…&at=<timestamp>` → `{ "variants": [ { "variantId", "sku", "stock" } ] }`:
  every variant of the shop with its stock at that moment (0 before it existed).
- The movements of a variant always add up to its stock, also when many orders arrive at the same
  moment.

# 6. Sales reports
Shop owners want numbers: what sold per month, which categories and sizes sell best, what the
discount codes cost them and how much went back.

`GET /reports/sales?shopId=clay-and-kiln&groupBy=<keys>&from=2026-10-01&to=2026-12-31`

- `shopId` and `groupBy` are required → `400` without them.
- `from` and `to` are optional dates (`YYYY-MM-DD`, inclusive), compared with the UTC date of the
  order's `createdAt`. Invalid dates → `400`.
- The report covers the lines of orders that aren't cancelled.
- `groupBy` is a comma-separated list of keys:
  - `day` (`YYYY-MM-DD`) and `month` (`YYYY-MM`): of the order's `createdAt`, in UTC
  - `productId`, `variantId`
  - `category`: the product's current category
  - `option.<name>`: the line's variant option (as ordered)
  - `attr.<key>`: the product's current attribute value
  - `discountCode`: the order's discount code, written as the shop defined it

  An unknown key → `400`. Lines without a value for a key are grouped under `null`.
- Reports always reflect the current data; e.g. when a product moves to another category, its sales
  move with it.

Response, one entry per combination of values that has at least one line:
```json
{
  "groups": [
    { "category": "mugs", "month": "2026-12", "orders": 12, "units": 30, "gross": 735,
      "discounts": 40.5, "refunds": 24.5, "net": 670 }
  ]
}
```
- One property per `groupBy` key, named exactly like the key.
- `orders`: the number of different orders with lines in the group.
- `units`: the quantities ordered minus the units returned.
- `gross`: the sum of the line totals. `discounts`: the sum of the lines' discounts. `refunds`: the
  sum of what was refunded for the lines. `net`: `gross` − `discounts` − `refunds`.
